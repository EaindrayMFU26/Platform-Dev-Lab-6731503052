1. Problem and Capability

Problem. The Campus Equipment Booking API from the midterm lets students and staff reserve projectors, cameras and meeting rooms. Around such a service people send support messages: "the projector will not turn on", "can I move my booking to Tuesday", "I cannot log in". Without help, a staff member reads every message and decides who should handle it and how fast. The capability reads one free-text message and decides, in a structured way, (1) which queue should handle it, (2) how urgent it is, and (3) whether a person must read it before anything happens automatically. The platform then files the message as a ticket in that queue, so staff see sorted work instead of an inbox.

Why AI? The input is free text, in English or Thai, with typos, feelings and no fixed vocabulary. Deterministic rules need a keyword list per queue, and such rules failed on four of the thirteen test inputs: on negation ("I don't want to cancel anything, I just want to know whether the camera comes with a tripod" contains "cancel"), on a message without any queue keyword ("Someone else is using the meeting room I booked and my presentation starts in 5 minutes"), on a safety problem described in words nobody put on the list ("sparking", "smells like burning plastic"), and on a word used in a different role (a question that merely mentions an "equipment fault"). The keyword rules written for the fallback chose the expected queue for 9 of the 13 test inputs; the model chose it for 13 of 13 (section 2). A decision model also returns a probability for every option, which rules cannot, and that probability is what lets the platform decide when to act automatically and when to ask a person.

A decision model (Jev, or Clef here) fits better than a chat model because the answer must be one of a fixed set of labels with a probability. Such a model can only answer with the options it is given: there is no prose to parse and no invented label, and in the tests the same input always gave the same answer.

Input. One JSON object:

Field Type Rule
message string Required. The support message. Not blank, at most 2000 characters, no control characters except tabs and line breaks.
context.equipmentId string Optional. The equipment the message is about, for example eq-2. At most 64 characters; when a ticket is filed it must exist.
context.bookingId string Optional. The booking the message is about. At most 64 characters. 
{ "message": "Camera B is not turning on and I need it for a shoot in 30 minutes!!", "context": { "equipmentId": "eq-2" } }

Expected output. One routing decision with three decisions and the evidence behind them:

Decision Allowed values Comes from
queue booking_change, equipment_fault, access_or_account, general_question the model's choice question (4 choices)
urgency low, normal, high the model's score question (3 ordered levels)
needsHuman true, false the model's yes/no (noul) probability, combined with a confidence threshold

The decision also carries confidence (0 to 1), source (model or fallback), model and fallbackReason. A details object holds every probability, the reasons, the latency and the token count. The full schema is in section 2. The downstream action is a ticket row in the support_tickets table that staff read per queue.

2. Decision Implementation

Decision configuration. The capability asks the model three typed questions about one state. This is the exact object sent to the model, DECISION_QUESTIONS in src/support-router.ts:

{
  "queue": {
    "type": "choice",
    "instructions": "Which support queue should handle this message sent to the campus equipment booking service?",
    "criteria": {
      "booking_change": "The sender wants to create, move, extend, shorten or cancel a booking, or reports a booking conflict or double booking",
      "equipment_fault": "The equipment or room facilities are broken, missing, damaged or not working",
      "access_or_account": "The sender cannot log in, is not authorised, or has an account, student ID or permission problem with the booking system",
      "general_question": "A question about rules, availability, policies or how to use the service, or anything that fits no other queue"
    }
  },
  "urgency": {
    "type": "score",
    "instructions": "How urgent is this message?",
    "criteria": [
      "Low: no deadline mentioned, can wait several days",
      "Normal: should be handled within one working day",
      "High: the sender is blocked right now or within the next few hours"
    ]
  },
  "needs_human": {
    "type": "noul",
    "instructions": "A staff member must read this message personally before any automatic action is taken, for example because it is ambiguous, a complaint, a safety problem, or fits no queue well."
  }
}

The state is the message plus a one-line description of the service and the optional ids. The complete request body built by buildDecisionRequest() and passed to env.AI.run("@cf/cloudflare/clef", ...):

Why Clef, and how it relates to Jev. Jev could not be called in this work: no TypeSafe account or API key was available in the session that built it. Clef was used instead because it runs on the Cloudflare account the project already uses. The two are different models: Clef is Cloudflare's own 27-billion-parameter decision model, not a version of Jev. What they share is the interface. Cloudflare documents Clef as taking "a state and a schema of typed questions" and describes its image field as a "Clef extension to the System One API", the API on which TypeSafe serves Jev (POST https://api.typesafe.ai/v1/systemone). Both take the same { model, state, questions } body with the same choice, score and noul questions, and both answer with the same fields (choice, probabilities, confidence, score, legend, noul). The equivalence is therefore one of protocol, not of measured decision quality.

docs/A6/jev-request.json is the request above with "model": "jev-latest", for TypeSafe's API (bearer key). A unit check keeps that file identical to what the code builds. For OpenRouter's POST https://openrouter.ai/api/alpha/decisions the model is typesafe/jev-1.14, and the same questions are valid there: OpenRouter's schema requires only type and instructions on a noul question and accepts an optional criteria object with "true" and "false" keys. Jev answers in the same shape, so the validation and policy code would not change. Jev itself was not run for this report.

How the code uses the answer (src/support-router.ts, no HTTP and no database in it):

  1. validateSupportRequest() checks the input (section 3).
  2. routeSupportRequest() calls the model through a small ModelRunner interface with a time limit (ROUTER_TIMEOUT_MS, 8000 ms).
  3. parseModelAnswers() validates the answer against the schema. The three answers must be present with the right type. The chosen queue must be one of the four labels and must be the most probable one. Every label must have a probability between 0 and 1, and they must add up to 1 (tolerance 0.05). The urgency score must be a number from 0 to 2 with probabilities for the three levels, and the noul value must be a probability. Anything else is rejected.
  4. decideFromModel() applies the policy: queue = the model's choice; urgency = the most probable level; needsHuman = the yes/no probability is at least 0.5 or the model's confidence in the queue is below ROUTER_MIN_CONFIDENCE (0.6).
  5. If step 2 fails or times out, or step 3 rejects the answer, fallbackDecision() decides with keyword rules and marks the result (section 3).

Output schema. Both the model and the fallback produce exactly this object (TypeScript type RoutingDecision):

Field Type Values and meaning
queue string, required booking_change | equipment_fault | access_or_account | general_question
urgency string, required low | normal | high
needsHuman boolean, required true when a person must read the message first
confidence number 0..1, required the model's confidence in the queue; 0 for the fallback
source string, required model | fallback
model string or null @cf/cloudflare/clef for a model decision, null for the fallback
fallbackReason string or null null, or model_unavailable | model_error | model_timeout | invalid_model_output
details.queueProbabilities object one probability per queue, summing to 1 within 0.05 (all 0 for the fallback)
details.urgencyScore number 0..2 probability-weighted urgency
details.urgencyProbabilities object low, normal, high
details.needsHumanProbability number 0..1 the model's answer to the noul question (1 for the fallback)
details.reasons string[] why a person is needed, or why the fallback decided and what it matched (error texts of the AI service cut to 200 characters)
details.latencyMs, details.inputTokens, details.reportedModel number, number or null, string or null measured inside the Worker; token usage and model name as reported by the service

3. Platform Integration

Architecture.

The flow for one message:

  1. The user's client sends POST /api/support/tickets with the message and optional context.
  2. The application (the existing Hono Worker) validates the input and answers 413, 400 or 404 when it is wrong. Nothing is sent to the model for an invalid request.
  3. routeSupportRequest() builds the state and the three questions and calls the decision model through the Workers AI binding with an 8 s limit. The answer is validated against the schema and turned into a decision by the policy. If the model is unavailable, fails, is too slow or answers with something that does not fit, the deterministic fallback decides instead.
  4. The downstream action: the ticket is stored in D1 (support_tickets) with the queue, urgency, needs-a-person flag, source and the full decision as JSON, and 201 Created returns the ticket with its decision. Staff read GET /api/support/tickets?queue=<name>, newest first. Tickets with needsHuman: true are flagged for a person to read before any automatic reply or action; the staff process that acts on the flag is not part of this build.

POST /api/support/route returns the decision without storing anything, for testing and for clients that do their own follow-up. The arrow from the Worker to Workers AI is a trust boundary: the message text leaves the application there and is processed by Cloudflare.

Validation rules.

Input (validateSupportRequest(), all problems reported together in one 400 message):

The length limit also bounds what is sent to the model (about 520 tokens for a typical message).

Output (parseModelAnswers(), applied to every model answer before it is used):

Check If it fails
The response has an answers object with queue, urgency and needs_human of the right type fallback, invalid_model_output
queue.choice is one of the four labels, and the most probable of them fallback (an invented or self-contradicting label is never stored)
every queue has a probability in 0..1 and they add up to 1 (tolerance 0.05); confidence is in 0..1 fallback
urgency.score is a number from 0 to 2, with probabilities for levels 0, 1, 2 that add up to 1 fallback
needs_human.noul is a probability fallback
The stored row: CHECK constraints on queue, urgency, needs_human, confidence, decision_source, and json_valid on the stored decision the database rejects the write (never reached through the API)

Policy on a valid answer: urgency is the most probable level. needsHuman is true when the noul probability is at least 0.5 or the confidence in the queue is below 0.6. The 0.6 threshold is a setting (ROUTER_MIN_CONFIDENCE), and the reasons are written into details.reasons.

Fallback strategy. The capability never fails because of the model: routeSupportRequest() always returns a complete decision, and a model failure is never an HTTP error.

Assignment case fallbackReason How it is detected Demonstrated in
Service unavailable: no AI binding configured model_unavailable env.AI is undefined unit tests (fake: no runner)
Model failure: the call throws (unknown model, service error, daily allowance used up) model_error the error from the binding is caught HTTP run against a server with a model id that does not exist (SUPPORT_ROUTER_FALLBACK_EVIDENCE.md); unit tests
Service too slow or not answering model_timeout no answer within ROUTER_TIMEOUT_MS (8000 ms) HTTP run against a server with a 1 ms limit (SUPPORT_ROUTER_TIMEOUT_EVIDENCE.md); unit tests
Invalid result: wrong shape, unknown or self-contradicting label, bad probabilities invalid_model_output parseModelAnswers() rejects it unit tests (fakes that answer with the label refunds, a label their own probabilities rank low, or plain text)

A real outage of Workers AI would appear as model_error or model_timeout; model_unavailable means the binding is missing from the configuration. The real model was not made to return an invalid answer (the malformed requests in the probe were refused with an error, which is the model_error path), so that case is shown with fakes.

The fallback itself is deterministic keyword rules (keywordRoute()). Each queue has a list of English and Thai keywords, for example password and student id for access, not turning on and เปิดไม่ติด for faults, cancel and rescheduled for booking changes. The queue with the most hits wins. On a tie an access problem beats a fault, because the fault list includes general phrases such as "doesn't work" that also appear in login complaints, and a fault beats a booking change. No hit means general_question. Urgency is high when an urgency word (minutes, today, ด่วน, ...) appears, low for a general question, and normal otherwise. Whatever the rules decide, needsHuman is true and confidence is 0. The result says "source": "fallback" with the reason and the matched keywords, so nothing downstream can mistake it for a model decision, and it is always flagged for a person. Each fallback is also logged on the server, without the message text.

4. Engineering Reflection

This reflection was drafted by the AI from the recorded evidence.

What worked. The typed-question protocol removed the usual prompt work. The three questions and their criteria were written once and never changed, and the model chose the expected queue for all thirteen inputs. That includes the Thai message, the negation case that defeats keyword rules, and two attempts to steer it with instructions hidden in the message (the second was added after its answer had been seen). The probabilities worked as a control signal without tuning. Nonsense input came back with confidence 0.12 and went to a person. The first injection attempt was routed as a general question, but with confidence 0.57, so the threshold sent it to a person too. Identical input gave identical answers: within a run (the repeat of input 1, and the ticket for input 2) and across three runs between 12:31 and 14:35 UTC (the same decisions and confidence values for the twelve original inputs). That makes the tests repeatable and an audit possible. The model is fast and cheap for this use: about 0.3 to 1.4 s and 520 input tokens (about 11 neurons, roughly $0.00012) per decision in the final run. The capability lives in a pure module behind a tiny ModelRunner interface, which made the failure paths easy to test with fakes (78 unit checks, no network). The HTTP layer is the same for a model decision and a fallback decision, so the API never fails because the model does.

Unexpected behaviour or mistakes.

  1. Urgency is the weakest decision. For input 9 ("the projector I booked for tomorrow is broken") and input 10 (the repeated complaint) the model answered high where normal was expected. In three cases (inputs 3, 10 and 13) the most probable urgency level had a probability of only about 0.5 or less. The level descriptions ("within the next few hours") need sharper wording with examples.

  2. More requests for a person than expected (10 of 13 agreement). On inputs 2 and 9 the noul probabilities were 0.61 and 0.57, just above the 0.5 line. Values near a single threshold flip easily. A band would be more stable: automatic below 0.35, a person above 0.65, and "review when convenient" in between.

  3. The injected note may have shifted the urgency, but this was not measured. In input 13 the queue (0.97) and the request for a person (0.82) held, but "low" urgency got 0.35 against 0.47 for "high", with "normal" least likely (0.18). The same message without the note was not run, so it is not known how much of this the note caused. The "low" level means "no deadline mentioned" and this message names none. The other fault messages got 0.01 to 0.04 for "low", and the repeated complaint (input 10), which names no deadline either, got 0.17.

  4. Less certainty in Thai. The Thai message was routed correctly, but with a lower confidence (0.82) than comparable English messages (about 0.95). One Thai input is not enough to say more.

  5. Engineering mistakes found in two reviews. Two reviews of the work by separate AI agents found mistakes that the test runs had not caught.

    • Code: an empty ROUTER_MIN_CONFIDENCE setting switched the confidence check off. In the fallback, typographic apostrophes (doesn’t) and general phrases like "doesn't work" misled the keyword rules, and Thai fee words that begin with เสีย counted as "broken".
    • Tests: the unit-test fixture had been recorded with an earlier request shape, and some unit checks could not fail or did not test the limit they named.
    • Documents: a diagram label, a reference and several sentences claimed more than the evidence showed. The AI's first probe also misread Cloudflare's documentation: it sent the selector clef-flash to the clef model, which correctly refused it.

    All of these were fixed or corrected, and every test was re-run, before this report. The list is in AI_LOG.md.

Production risks.

  1. No authentication and no rate limit. Anyone who can reach the API can read and delete every ticket. Every routing request also spends model tokens from the account's daily allowance: 10,000 neurons, about 880 decisions on the free plan. A simple loop could use the allowance up. After that every decision would become a fallback (model_error; this is expected from Cloudflare's documentation, but was not tested), routing quality would drop to the keyword level, and every ticket would need a person. A staff login for the ticket routes and a rate limit are needed before public exposure, and source and fallbackReason should be monitored.
  2. Personal data. Messages can contain names and student ids. They are sent to a third-party model and stored without a retention limit. Thailand's Personal Data Protection Act B.E. 2562 (2019) is likely to apply, including its rules on sending personal data abroad. This needs a legal review, a retention rule, an access rule and a notice to users.
  3. Adversarial text. The model cannot produce anything but labels and probabilities, but a sender may be able to push those probabilities (input 13 fits that, without a control run to prove it). No irreversible action may depend on needsHuman: false alone. Messages may also contain bidirectional-text control characters, which the validation accepts and which can make a message display differently. Message text and the stored reasons must therefore be shown to staff as plain text, never as HTML.
  4. Model drift. The model name clef has no version, so an update on Cloudflare's side can shift the probabilities and make the 0.5 and 0.6 thresholds wrong. The thirteen inputs should be re-run on every change, and a labelled evaluation set should be built from real messages.
  5. Unmeasured thresholds and unequal costs. The thresholds were chosen by the AI's judgement. A fault routed to the general queue delays a repair more than the reverse mistake costs, and the policy does not reflect that yet.
  6. A weak fallback for safety. The keyword rules miss safety reports written in unexpected words (input 13). The keyword lists need maintenance in two languages, and one provider hosts both the service and the model.

Next improvement. First, add a staff login and a per-user rate limit, with a daily budget guard that switches to the fallback early instead of exhausting the allowance mid-day. Log source, fallbackReason, latency and tokens, with an alert on the fallback rate. Second, collect real messages together with the queue a staff member actually chose, and build an evaluation set from them. Measure precision and recall per queue, then tune the thresholds (including a two-level band for needsHuman) and the score criteria on that data. Run input 13 without the note as a control case. Add safety words (spark, smoke, burning, ไหม้) to the fallback with a forced high urgency. Third, run the same configuration on Jev to compare its probabilities with Clef's, deploy this version to Cloudflare, and re-run the evidence against the live URL.
