## 4. Decisions the AI made

These were the AI's choices, not requirements of the brief. Each one is explained in
`API_CONTRACT.md` ("Required behaviour and optional choices", "Assumptions") or `SCHEMA.md`.

- An unknown `equipmentId` returns 404 rather than 400.
- A booking may start exactly when another ends (the end time is exclusive).
- Date-times must include a time zone and are stored and returned in UTC.
- Bookings in the past are allowed; there is no minimum or maximum length.
- All five fields are required on create; text is trimmed; limits of 64, 100 and 500 characters.
- Booking ids are random UUIDs; unknown properties in a request body are ignored.
- The overlap check and the write are one SQL statement instead of a check followed by an insert.
- Times are stored as text with a `CHECK` on the format, not as numbers.
- The overlap rule is not also enforced by database triggers.
- CORS allows every origin.
- The names of the Worker (`equipment-booking-api`) and of the D1 database
  (`equipment-booking-db`). Cloudflare placed the database in its APAC region automatically.

## D. Decisions the AI made

These were the AI's choices, not requirements of the assignment. Where each is explained is in
brackets.

- The problem: routing support messages for the existing booking API, instead of a new project.
- The model: `@cf/cloudflare/clef` on Cloudflare Workers AI as the "equivalent decision model".

- Four queues, three urgency levels and one yes/no question, and their wording. The wording was
  written once and not tuned against the test results. (Report, section 2)
- The policy: urgency is the most probable level; a person is needed when the yes/no probability is
  at least 0.5 or the confidence in the queue is below 0.6. Both thresholds were chosen by judgement,
  not measured. (Report, sections 2 and 4)
- The fallback: keyword rules in English and Thai; every fallback decision is flagged for a person
  and has confidence 0. On a tie an access problem beats a fault, which beats a booking change; the
  first version put the fault first (section E). (Report, section 3)
- An 8 second time limit. A timed-out model call is not cancelled, only ignored.
  (`src/support-router.ts`)
- `POST /support/route` does not look up `context.equipmentId`; `POST /support/tickets` does (404).
  `context.bookingId` is never looked up. (`API_CONTRACT.md`)
- Limits: 2000 characters per message, 16 KB per request body (413), control characters refused,
  the error text of the AI service cut to 200 characters. A fallback writes a warning to the server
  log without the message text. (`API_CONTRACT.md`)
- The decision is stored twice in `support_tickets`: as columns for filtering and as JSON for
  auditing. `booking_id` has no foreign key. (`SCHEMA.md`)
- The evidence was produced against the local server; the deployed Worker was not updated.

## D. Decisions the AI made

- **The improvement:** more relevant grounding context, one of the four options in the assignment.
  It was chosen from the A6 findings (urgency was the weakest decision) and planned before the
  baseline ran, because Task 1 asks for the context first. It is switched by `ROUTER_GROUNDING`,
  default off, so the default behaviour stays A6.
- **The knowledge base:** 10 records written by the AI as the rules of this lab platform. Facts such
  as the 50 baht fine, 14 days ahead, 4 hours, 2 active bookings and 10 seats were made up for the
  platform; they are not a real university policy, and the report says so.
- **Retrieval:** keyword scoring with the fallback's matching; two records always, up to three more
  by score, a tie to the record listed first; no vector database.
- **Evaluation design:** 10 cases written by the AI, with expected results derived from the
  knowledge base. The report names the resulting circularity as a limit. Correct means all three
  decisions (and, for the fallback cases, the fallback reason). Every case runs 5 times, in rounds,
  timed by curl's `time_total`, after one warm-up request per server. p95 is nearest-rank over the
  50 requests. Cost = measured input tokens × the published price.
- **Fallback cases** reach the fallback through separate servers: a model id that does not exist
  (port 8789) and a 1 ms time limit (port 8790), as in A6.
- **A response field,** `details.contextRecords`, so that the evidence shows the context of every
  decision and the runner can check which variant answered.
- **The minor A6 issues** from the last check (part 2) were not fixed, so that the baseline stays
  exactly the A6 capability and the A6 evidence stays valid.
- **An interleaved latency check** was added after the two runs, because the time inside the Worker
  varied from round to round and the runs were made at different times.

## E. Problems found, and how they were handled

- **Freezing:** the knowledge base and the 10 cases were written first and frozen at 15:00:17 by
  recording their SHA-256 hashes, before any evaluation run. Before freezing, the AI checked the two
  fallback expectations against the deterministic keyword rules; both matched as written. Both run
  logs and `eval/COMPARISON.md` repeat the hashes, and they are unchanged; the interleaved latency
  check does not record them. The freeze record is `eval/FREEZE.txt` (see the review below).
- **Importing TypeScript in Node:** Node could not import `./text-match` without the `.ts`
  extension. The import now names the extension, and `tsconfig.json` allows it.
- **Invisible characters:** the file-writing tool had turned some `\u` escape sequences into the
  literal characters (zero-width space, right-to-left mark, BOM, curly apostrophes). This had also
  happened in A6: in the two character classes of the normalising function and in some unit-test
  strings. The behaviour was correct, but the source was hard to read. In `src/text-match.ts` the
  classes are now written as ASCII escapes; the A6 test files were left unchanged.
- **The last A6 check overlapped with A7:** it was still running when the A7 code was installed
  (15:11). It reported, correctly, that the A6 documents no longer describe the code in the folder
  exactly. This was handled by documenting the A7 additions as later changes in the README and API
  contract, and by keeping the A6 snapshot zip.
- **Two dev servers answering for each other:** the first attempt at the latency check stopped at
  its first request. The "baseline" server on port 8787 answered with grounding on. Two causes:
  - Stopping the earlier servers with the tool had left their processes running.
  - Two local sessions of the same Worker name share wrangler's registry entry, so one session
    answered the other session's port.

  The check's guard stopped it before anything was recorded. All servers were then stopped, and the
  grounded server was started under its own Worker name; the script's header now says so. The two
  evaluation runs were not affected:
  - In each run, every port behaved as its own configuration requires: model answers on 8787, a
    model error on 8789, a timeout on 8790. No other session could have produced that.
  - The baseline servers were stopped before the improved ones were started.
- **Review of the A7 work:** after the report was first built, AI review agents checked the report,
  the code and the evidence. They reported 28 findings, none of high severity. The three most
  serious were checked again by separate agents: one was confirmed, two were rejected, and the rest

    used a median method found nowhere else in the report (the upper of the two middle values) and

    report, the README and this log now say so and give the mean difference (-23.8 ms); the report
    also gives the mean of the two middle values (20.4 ms) and states once that every median and
    percentile in it is nearest-rank.
  - Wrong statements in the report: "four of the five failures are urgency" (all five are, and T09
    also has the wrong queue); "only KB09 contains that rule" (KB01 does too, but was not retrieved
