# API Contract: Campus Equipment Booking API

This contract follows the Common API Contract in [exam_brief_en.md](exam_brief_en.md). Where the
brief leaves something open, the decision is listed under [Assumptions](#assumptions), each with
the test case that verifies it.

- **Base URL (deployed):** `https://equipment-booking-api.medcard-api.workers.dev/api`
- **Base URL (local):** `http://localhost:8787/api`
- **Format:** every request and response body is JSON (UTF-8)
- **Times:** ISO 8601 date-times, always returned in UTC as `YYYY-MM-DDTHH:mm:ss.sssZ`
- **Errors:** always `{ "error": "<message>" }` with a 4xx or 5xx status, never 200

## Endpoints

| Method | Path | Success | Errors | Purpose |
|---|---|---:|---|---|
| `GET` | `/equipment` | 200 | | List equipment |
| `GET` | `/bookings` | 200 | | List bookings |
| `GET` | `/bookings/:id` | 200 | 404 | Get one booking |
| `POST` | `/bookings` | 201 | 400, 404, 409 | Create a booking |
| `PATCH` | `/bookings/:id` | 200 | 400, 404, 409 | Update a booking |
| `DELETE` | `/bookings/:id` | 204 | 404 | Delete a booking |

Resources are nouns and the HTTP method is the verb. `OPTIONS` on any path answers a CORS preflight
with 204 (see the README). `GET` on the base URL itself returns 200 with a short index of these
routes; it is a convenience for people who open the link and is not part of the common contract.

## Data shapes

### Equipment

| Field | Type | Example |
|---|---|---|
| `id` | string | `"eq-1"` |
| `name` | string | `"Projector A"` |
| `location` | string | `"Building 1"` |

### Booking

| Field | Type | Sent by client | Rules |
|---|---|---|---|
| `id` | string (UUID) | never | Generated by the server. Ignored if sent. |
| `equipmentId` | string | required on create | Must be the `id` of existing equipment. At most 64 characters. |
| `borrowerName` | string | required on create | Not blank. At most 100 characters. Surrounding spaces are removed. |
| `startAt` | string, ISO 8601 date-time | required on create | Must be a real date-time with a time zone (`Z` or an offset such as `+07:00`). Seconds and up to three decimals of a second are optional. |
| `endAt` | string, ISO 8601 date-time | required on create | Same format as `startAt`, and must be later than `startAt`. |
| `purpose` | string | required on create | Not blank. At most 500 characters. Surrounding spaces are removed. |
| `createdAt` | string, ISO 8601 date-time | never | Set by the server. |
| `updatedAt` | string, ISO 8601 date-time | never | Set by the server on every update. |

A booking occupies the time from `startAt` up to, but not including, `endAt`. The text fields
(`equipmentId`, `borrowerName`, `purpose`) must not contain NUL characters.

## Endpoint details

### `GET /equipment`

`200 OK`

```json
[
  { "id": "eq-1", "name": "Projector A", "location": "Building 1" },
  { "id": "eq-2", "name": "Camera B", "location": "Media Lab" },
  { "id": "eq-3", "name": "Meeting Room C", "location": "Building 2" }
]
```

### `GET /bookings`

`200 OK` with an array of bookings ordered by `startAt`. An empty array when there are none.

### `GET /bookings/:id`

`200 OK` with the booking, or `404` when no booking has that id.

### `POST /bookings`

Request body (all five fields are required):

```json
{
  "equipmentId": "eq-1",
  "borrowerName": "Somchai Jaidee",
  "startAt": "2026-10-20T09:00:00.000Z",
  "endAt": "2026-10-20T11:00:00.000Z",
  "purpose": "Class presentation"
}
```

`201 Created`

```json
{
  "id": "41e99671-90a3-4557-9187-d9f742e4d060",
  "equipmentId": "eq-1",
  "borrowerName": "Somchai Jaidee",
  "startAt": "2026-10-20T09:00:00.000Z",
  "endAt": "2026-10-20T11:00:00.000Z",
  "purpose": "Class presentation",
  "createdAt": "2026-10-06T07:49:19.760Z",
  "updatedAt": "2026-10-06T07:49:19.760Z"
}
```

| Status | When | Example `error` |
|---:|---|---|
| 400 | Body is not a JSON object | `Request body must be a valid JSON object` |
| 400 | A field is missing, blank, too long or of the wrong type | `borrowerName is required; purpose is required` |
| 400 | `startAt` or `endAt` is not a valid date-time | `startAt must be an ISO 8601 date-time with a time zone, e.g. 2026-10-20T09:00:00.000Z` |
| 400 | `startAt` is not before `endAt` | `startAt must be before endAt` |
| 404 | `equipmentId` does not match any equipment | `Equipment 'eq-999' not found` |
| 409 | The equipment is already booked for part of that time | `Equipment 'eq-1' is already booked from 2026-10-20T09:00:00.000Z to 2026-10-20T11:00:00.000Z` |

All validation problems are reported together in one message, separated by `; `.

### `PATCH /bookings/:id`

Request body: any one or more of the five booking fields. Fields that are left out keep their
stored value. Every rule is then checked on the resulting booking, so changing only `endAt` is
still compared with the stored `startAt`, and the overlap check ignores the booking being updated.

```json
{ "endAt": "2026-10-20T12:00:00.000Z", "purpose": "Thesis defence" }
```

`200 OK` with the full updated booking.

| Status | When |
|---:|---|
| 400 | Body is not a JSON object, contains none of the five fields, a sent field is invalid, or the result would have `startAt` not before `endAt` |
| 404 | No booking has that id, or the new `equipmentId` does not exist |
| 409 | The new time or the new equipment overlaps another booking |

### `DELETE /bookings/:id`

`204 No Content` with an empty body, or `404` when no booking has that id.

## Errors

Every error, including unknown routes and unexpected server failures, has this exact shape and no
other properties:

```json
{ "error": "A message understandable to a user or developer" }
```

The HTTP status code is the machine-readable part; the message is for people.

### Why 400, 404 and 409

| Status | Meaning in this API | What the client should do |
|---:|---|---|
| **400 Bad Request** | The request itself is wrong: unreadable JSON, a missing or invalid field, or a start time that is not before the end time. Sending it again unchanged will always fail. | Fix the payload. |
| **404 Not Found** | The request is well formed, but it points at something that does not exist: the booking id in the URL, the `equipmentId` in the body, or the route. | Use an id that exists. |
| **409 Conflict** | The request is valid and everything it refers to exists, but it collides with data already stored: another booking of the same equipment overlaps the requested time. The same request would succeed for a free slot, which is what separates 409 from 400. | Choose another time or other equipment. |
| **500 Internal Server Error** | Something unexpected failed on the server. The response says only `Internal server error`; the details stay in the server log. | Retry later or report it. |

Success codes: `200` for reads and updates, `201` when a booking was created, `204` when a delete
succeeded and there is nothing to return.

### Order of checks

When a request has more than one problem, the first matching row decides the status.

| | `POST /bookings` | `PATCH /bookings/:id` |
|--:|---|---|
| 1 | 400: body and fields | 400: body and fields |
| 2 | 404: equipment exists | 404: booking exists |
| 3 | 409: time is free | 400: resulting `startAt` is before `endAt` |
| 4 | | 404: new equipment exists |
| 5 | | 409: time is free |

## Required behaviour and optional choices

**Required by the brief.** These are fixed and must not change:

- The six routes and their success codes: 200 for reads and updates, 201 for create, 204 for delete.
- The five-field booking payload, and responses that include at least `id` and those five fields.
- `equipmentId` must exist, `startAt` must be before `endAt`, and bookings of the same equipment
  must not overlap, on create and on update.
- Errors as `{ "error": "..." }`: 400 for missing or invalid data, 404 when a resource is not
  found, 409 for a time conflict.
- At least two equipment records, and SQL parameter binding.

**Optional choices made in this implementation.** These could be changed without breaking the
brief:

- 404 rather than 400 for an unknown `equipmentId` (assumption 1).
- The end time is exclusive, so back-to-back bookings are allowed (assumption 2).
- Times must carry a time zone, offsets are accepted, and everything is stored in UTC
  (assumption 4).
- The length limits (64, 100 and 500 characters) and the trimming of text fields.
- The extra response fields `createdAt` and `updatedAt`, and UUIDs as booking ids.
- All validation problems reported in one message, unknown properties ignored, and an empty
  `PATCH` rejected.
- Bookings listed in order of `startAt`.
- How the overlap rule is implemented: one SQL statement that checks and writes.
- Database constraints (foreign key, `CHECK`) in addition to the validation in the API.
- CORS, which the brief makes optional. It is enabled because a browser-based client is used
  (see the README).
- The index returned by the base URL, the rejection of NUL characters in text, and the limit of
  three decimals of a second in times.

## Assumptions

The brief does not settle these points. Case numbers refer to [TEST_EVIDENCE.md](TEST_EVIDENCE.md).

| # | Assumption | Why | Verified by |
|--:|---|---|---|
| 1 | An `equipmentId` that does not exist returns **404**, not 400. | The payload is valid; the resource it refers to is missing, which is the brief's definition of 404. The choice is made in two lines of [src/index.ts](src/index.ts) (the two `Equipment '...' not found` responses) if 400 is required instead. | Cases 13, 22 |
| 2 | A booking may start at the exact moment another one ends. | The end time is exclusive, so 09:00-11:00 and 11:00-13:00 do not share any time. | Case 19 |
| 3 | Two bookings overlap only if they are for the **same** equipment. | The brief says "bookings for the same equipment must not overlap". | Case 18 |
| 4 | Date-times must carry a time zone and are stored and returned in UTC. | A time without a zone is ambiguous. One zone and one fixed format also make comparisons reliable. Offsets such as `+07:00` are accepted and converted. | Cases 8, 27 |
| 5 | Impossible dates such as 30 February are rejected with 400. | JavaScript would silently move the booking to 2 March. | Case 9 |
| 6 | Bookings in the past and bookings of any length are allowed. | The brief sets no such limits, so none were invented. | Not restricted |
| 7 | All five fields are required on create, and text fields must not be blank. | The brief gives one payload for creating a booking and asks for 400 on missing data. | Case 6 |
| 8 | Properties other than the five booking fields are ignored. Clients cannot set `id`, `createdAt` or `updatedAt`. | Only a fixed list of fields is ever read from the body. | Code: `FIELDS` in [src/validation.ts](src/validation.ts) |
| 9 | `PATCH` is a partial update and must change at least one field. | That is what PATCH means; an empty PATCH is almost certainly a client mistake. | Cases 5, 12 |
| 10 | Booking ids are opaque strings. An id that matches nothing is 404, whatever it looks like. | There is no "malformed id" case to separate from "not found". | Cases 14, 25 |
| 11 | Deleting a booking twice returns 204, then 404. | The second request finds nothing to delete. The stored data is the same after one call or many. | Cases 30, 32 |
| 12 | `GET /bookings` returns every booking as a plain array, without pagination or filters. | The contract defines the list responses as arrays. Pagination is noted as future work in the README. | Case 3 |
| 13 | There is no authentication. | The brief does not define users or roles. See "Security" in the README. | Not in scope |

### Retrying requests safely

`GET`, `PATCH` and `DELETE` can be repeated without changing the outcome. `POST` creates a new
booking each time it succeeds, but a repeated `POST` of the same booking cannot create a duplicate:
the first one holds the slot, so the repeat gets 409.
